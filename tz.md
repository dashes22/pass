# Техническое задание
## Кейс № 2. Система контроля сессий

### 1. Цель работы

Улучшить существующий сайт регистрации и входа пользователей. Добавить авторизацию с помощью двух токенов, страницу профиля и возможность безопасно завершить сеанс работы.

Обеспечить сохранение пользовательской сессии при закрытии вкладки или браузера, а также возможность одновременной работы двух пользователей под одной учётной записью с независимыми сессиями.

### 2. Используемые технологии

- **JWT** — создание и проверка Access Token.
- **Crypto** — создание случайного Refresh Token и его хеша.
- **SQLite** — хранение информации о пользовательских сессиях.

**Access Token** подтверждает, что пользователь вошёл в систему. Срок его действия составляет **15 минут**.

**Refresh Token** позволяет получить новую пару токенов без повторного ввода пароля. Срок его действия составляет **2 дня**.

Общий срок действия сессии не должен превышать 2 дней с момента входа.

Пример: пользователь вошёл в 12:00. В 12:15 Access Token истекает, но при действующей сессии его можно обновить. В 12:30 пользователь закрывает браузер. При повторном открытии сайта он автоматически получает новую пару токенов, если Refresh Token ещё действителен. Через 2 дня после входа потребуется авторизоваться повторно.

### 3. Функциональные требования

**3.1. Вход в систему**

- Сохранить существующую проверку логина и пароля.
- После успешного входа создать Access Token на 15 минут и Refresh Token на 2 дня.
- Передать Access Token приложению, а Refresh Token — в постоянную cookie.
- В базе данных создать отдельную запись сессии: пользователь, хеш Refresh Token, время входа, последней активности и окончания сессии.
- Каждому новому входу присваивать уникальный идентификатор сессии.
- Не завершать другие действующие сессии при новом входе под той же учётной записью.

**3.2. Страница профиля**

- После входа открывать профиль с логином пользователя и кнопкой «Выйти».
- Перед выдачей данных профиля сервер проверяет Access Token и состояние сессии в базе данных.
- Без действующей авторизации данные профиля не выдавать.
- При успешном обращении к защищённому ресурсу обновлять время последней активности.

**3.3. Обновление токенов**

- Когда Access Token истёк, приложение автоматически запрашивает новую пару токенов с помощью Refresh Token.
- Сервер проверяет, что сессия существует и ещё действует.
- При обновлении выдавать новый Access Token и новый Refresh Token.
- Старый Refresh Token после успешного обновления делать недействительным.
- При повторном использовании старого Refresh Token отклонять запрос и завершать соответствующую сессию.
- Не продлевать общий срок сессии более чем на 2 дня с момента первоначального входа.
- Не обновлять токены после выхода или окончания сессии.
- При обновлении Access Token предыдущий Access Token должен становиться недействительным. Для этого сервер хранит в базе данных текущую версию токена и проверяет её при каждом защищённом запросе. При обновлении версия меняется, поэтому старый Access Token больше не принимается.

**3.4. Восстановление сессии после закрытия браузера**

- Refresh Token должен храниться в постоянной cookie, которая не удаляется при закрытии вкладки или браузера.
- При повторном открытии сайта приложение автоматически отправляет запрос на обновление токенов.
- Если Refresh Token действителен, сервер выдаёт новую пару токенов без повторного ввода логина и пароля.
- Если Refresh Token истёк или сессия завершена, пользователь должен войти повторно.
- Access Token хранится только в оперативной памяти приложения и не сохраняется для дальнейшего использования после закрытия браузера.

**3.5. Работа нескольких пользователей под одной учётной записью**

- Предусмотреть возможность одновременной работы двух пользователей под одной учётной записью.
- Для каждого входа создавать отдельную сессию с собственными Access Token и Refresh Token.
- Хранить отдельный хеш Refresh Token для каждой сессии.
- Обновление токенов одним пользователем не должно влиять на сессию другого.
- При выходе одного пользователя завершать только его текущую сессию.
- Завершение одной сессии не должно приводить к завершению остальных сессий учётной записи.

**3.6. Выход**

- При нажатии кнопки «Выйти» завершать текущую сессию пользователя.
- Удалять или деактивировать соответствующую запись в базе данных.
- Удалять Refresh Token из cookie.
- Очищать Access Token из памяти приложения.
- После выхода запрещать доступ к данным профиля даже по ранее выданному Access Token.
- Возвращать пользователя на страницу входа.

### 4. Требования к интерфейсу

- Оставить существующие страницы регистрации и входа.
- Добавить страницу профиля с логином и кнопкой «Выйти».
- При истечении Access Token автоматически пытаться обновить пару токенов.
- При повторном открытии браузера автоматически восстанавливать сессию, если Refresh Token действителен.
- Если сессия закончилась, показывать сообщение: «Сессия истекла. Войдите снова» и открывать страницу входа.
- Хранить Access Token только во время работы приложения, не сохраняя его в браузере для дальнейшего использования.
- Refresh Token хранить в постоянной cookie с параметрами безопасности.

### 5. Требования к безопасности

- Проверять подпись и срок действия JWT, а также наличие действующей сессии в SQLite.
- Refresh Token создавать с использованием криптографически стойкого генератора случайных чисел.
- В базе данных хранить только хеш Refresh Token, а не сам токен.
- Использовать ротацию Refresh Token при каждом обновлении.
- Обеспечить безопасное хранение Refresh Token в браузере с помощью параметров `HttpOnly`, `Secure` и `SameSite`.
- Защитить обновление токенов и выход из системы от CSRF-атак.
- Хранить секрет JWT в переменных окружения, а не в исходном коде.
- Не выводить пароли и токены в журналы сервера.
- Сохранить существующее хеширование паролей Argon2id и ограничение попыток входа.
- Обеспечить работу сайта через HTTPS для защиты паролей и токенов при передаче между браузером и сервером.
- Ограничить доступ к базе данных и секретам приложения.
- Предусмотреть возможность смены секретного ключа JWT и принудительного завершения всех сессий при подозрении на компрометацию сервера.
- После выхода или обнаружения повторного использования старого Refresh Token запрещать дальнейшее использование соответствующей сессии.

### 7. Модель угроз, последствия и способы защиты

#### 7.1. Угрозы, от которых предусмотрена защита

1. **Кража Access Token.** Посторонний может получить доступ к аккаунту. Для защиты срок действия токена ограничивается 15 минутами, а сервер дополнительно проверяет состояние сессии и версию токена.
2. **Кража Refresh Token.** Злоумышленник может использовать его для продления доступа к аккаунту. Для защиты токен хранится в защищённой cookie, а в базе данных сохраняется только его хеш.
3. **Использование просроченного токена.** Злоумышленник может попытаться войти с помощью старого токена. Сервер проверяет срок действия и отклоняет просроченные токены.
4. **Подделка Access Token.** Злоумышленник может попытаться создать поддельный токен для входа в чужой аккаунт. Для защиты сервер проверяет его подлинность с помощью секретного ключа.
5. **Повторное использование старого Refresh Token.** Злоумышленник может попытаться получить доступ с помощью ранее использованного токена. После обновления старый токен становится недействительным.
6. **Доступ после закрытия браузера.** При повторном открытии сайта пользователь не должен вводить пароль заново. Для этого Refresh Token хранится в постоянной cookie и позволяет восстановить сессию.
7. **Доступ после выхода из аккаунта.** Посторонний может попытаться воспользоваться токенами завершённой сессии. При выходе сервер завершает соответствующую сессию и запрещает дальнейшее использование её токенов.
8. **Одновременное использование одного аккаунта.** При работе двух пользователей под одной учётной записью обновление или завершение одной сессии не должно влиять на другую. Для защиты каждая сессия хранится отдельно.
9. **Выполнение действий через посторонний сайт.** Злоумышленник может попытаться выполнить действия от имени пользователя без его согласия. Для защиты используются SameSite-cookie и дополнительные CSRF-проверки.
10. **Компрометация сервера.** Злоумышленник может получить доступ к секретам приложения, базе данных и пользовательским сессиям. Для ограничения последствий необходимо ограничивать доступ к серверу и базе данных, не хранить секреты в исходном коде, использовать хеширование Refresh Token и предусмотреть смену ключей и принудительное завершение всех сессий после обнаружения взлома.

#### 7.2. Угрозы, защита от которых выходит за рамки проекта

1. **Вирусы на компьютере пользователя.** Вредоносные программы могут украсть пароли и другие данные. Для защиты необходимо использовать антивирусное программное обеспечение.
2. **Фишинг.** Пользователь может ввести свои данные на поддельном сайте. Для предотвращения таких ситуаций требуются дополнительные средства защиты и внимательность пользователя.
3. **DDoS-атака.** Злоумышленники могут отправлять большое количество запросов, из-за чего сервер перестанет работать. Для защиты требуется специальное оборудование или дополнительные сервисы.
4. **Полная компрометация сервера.** Если злоумышленник получил полный административный доступ к серверу, он может получить секретные ключи и управлять приложением. Полностью предотвратить такие последствия средствами данного проекта невозможно. Для восстановления безопасности потребуется устранить причину взлома, заменить секретные ключи и завершить все действующие сессии.
5. **Физический доступ к серверу.** Посторонний человек может получить доступ к оборудованию и хранящимся данным. Для защиты необходимо ограничивать физический доступ к серверу.
6. **Взлом браузера пользователя.** Злоумышленник может получить доступ к открытому аккаунту и пользовательским данным. Для защиты необходимо обеспечивать безопасность браузера и компьютера пользователя.
